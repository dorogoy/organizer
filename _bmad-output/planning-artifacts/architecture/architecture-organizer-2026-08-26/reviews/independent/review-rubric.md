# Rubric Review — ARCHITECTURE-SPINE.md (independent lens)

**Target:** `architecture/architecture-organizer-2026-08-26/ARCHITECTURE-SPINE.md`
**Inputs judged against:** `prd.md`, `addendum.md`, `EXPERIENCE.md`, `DESIGN.md`
**Reviewer:** independent rubric lens · 2026-08-26

## Verdict

**Accept with fixes** — an unusually disciplined spine whose invariants are mostly mechanically enforced, holed by one self-contradiction on its own state-mutation rule and by a silent dimension: nothing governs how the act log and the catalogue evolve across the install-on-top builds AD-18 mandates mid-window.

## Findings

### CRITICAL

**C-1 — The spine contradicts itself on its own state-mutation invariant.**
Consistency Conventions, *State — mutation*: "Only two shapes: append an act, or insert a pool fact. Everything else is derivation. **Settings are the single mutable record in the app.**"
Structural Seed, under the ERD: "`SETTINGS` is a **derived cache** over `setting_changed` acts, **not a mutable record** (AD-1)."
These are incompatible schemas, and AD-1's own Rule takes the second side ("an append-only log of user acts — **settings changes included**, so what the Time Bag was on day 5 is reconstructible from the export"). Two units reading the two rows build a mutable `settings` table and a projection over `setting_changed` respectively; the export then either carries the day-5 Time Bag or does not, and SM-C1's reading depends on which. This is precisely the divergence the spine exists to prevent, on the row an implementer reads first. Fix: delete the mutable-record clause and state the settings projection as the third read model.

**C-2 — Nothing governs the evolution of the log or the catalogue, while AD-18 mandates install-on-top upgrades mid-window.**
The whole product is a pure function of `(pool, acts, day, session)`. AD-2 forbids rewriting history. AD-18 requires "install on top" so the schema migration runs and data survives, during the same four weeks that produce the validation evidence. Three unowned questions follow, all of which fail silently:
- **Unknown act kinds and changed payloads.** If a build renames an act, adds a required field, or drops a kind, what does the core do with the old rows — skip, throw, or coerce? Two units will answer differently, and both answers change every derived read model retroactively. Forward-only tolerant interpretation is the only path AD-2 leaves open, and nobody has said so.
- **Catalogue entry identity across builds.** AD-3's tie-break is "least-recently-dealt, then by stable id", and `card_dealt` rows reference pool items instantiated from catalogue entries. AD-16 calls the catalogue "a versioned data file" but never says entry ids are stable across versions. A reissued id set makes the rotation, FR-31's non-repetition, and FR-5's three-different-days counter silently wrong on a phone that has been upgraded.
- **What a version bump is allowed to change.** Adding entries is safe; renaming, re-sizing or removing one is not, and the coverage-floor tool checks the count rather than the continuity.

Nothing in the twenty ADs, the conventions, `tool/`'s three checks or the round-trip property would catch any of this. Fix: one AD on log and catalogue compatibility — the core tolerates and ignores act kinds it does not know, act payloads are additive-only, and catalogue ids are permanent once shipped, with a `tool/` check diffing ids against the previous release.

### HIGH

**H-3 — AD-16's "exactly three fields" leaves no room for an id or a string, and collides with AD-15 and the i18n convention.**
"Each entry carries exactly three fields — size from the 1-3-5 taxonomy, cadence, zone-or-none — so the weave needs no conversion step." But AD-3 needs a **stable id** per entry, and addendum A12 requires the Spanish task names to be "shipped Spanish UI copy [that] go into the string table on the same terms as everything else", while AD-15 requires one flat externalised table and the conventions make the generated Spanish ARB *be* that audit table. So: does the asset hold Spanish text (breaking AD-15's audit surface and the second-locale deferral) or an ARB key (which is a fourth field)? The spine reproduced FR-31's phrasing instead of resolving the ambiguity it creates one level down. Fix: name the entry's fields as id + string key + the three classification fields, and say explicitly that no Spanish text lives in `assets/evergreen/`.

**H-4 — AD-7's and AD-12's seals are Dart-only; the Android manifest and the Gradle dependency surface have no owner.**
AD-7: "a CI check fails the build if any other file [imports an HTTP client]". AD-12: "No third-party SDK that opens a network destination may be added, for any reason." A Dart import check cannot see a Gradle dependency, a Kotlin socket in one of AD-11's two hand-written channels, or a native SDK that initialises itself from a manifest entry — which is exactly how Crashlytics, remote config and a "diagnostics" SDK arrive. Relatedly, AD-17 fixes the three **runtime** permissions but nothing constrains the **merged manifest**, which is the only place a transitive plugin can add `WAKE_LOCK` (forbidden by §7), `ACCESS_NETWORK_STATE`, or a second `RECEIVE_BOOT_COMPLETED` consumer — and AD-17's "rescheduled after boot" silently requires that permission without naming it. Fix: extend the checks to a merged-manifest permission allowlist plus a Gradle/pubspec dependency allowlist, and name INTERNET and RECEIVE_BOOT_COMPLETED as the manifest's closed set alongside the three runtime permissions.

**H-5 — Secret handling has no architectural owner.**
The BYOK key appears once, in the Stack table, as a package choice. Nothing fixes its boundary: the key must never reach the act log (`slice_requested` is in the vocabulary), never the export (AD-13's `AUTHORITATIVE/` list excludes it only by implication), never AD-12's crash log — whose field list is "stack and timestamp, no task text, no image paths" and says nothing about keys, prompts or request URLs — and never a logged URL, which matters concretely because at least one allowlisted provider takes the key as a query parameter. FR-28 requires "never in app preferences, never in the export, and never transmitted anywhere except to its own provider"; that is an invariant with three independent leak paths and no AD. Fix: fold the secret boundary into AD-7 or AD-12 (the key crosses only from keystore to the egress module's request builder; no other module may name it; the crash log carries no request, URL, header or prompt).

**H-6 — FR-26 series (d) has no home, and the act naming convention forbids the acts the spine itself needs.**
The convention reads "Past-tense verb phrases… **one per user act**", then lists `card_dealt` — which is not a user act. Series (d) requires "Ambient Invitation emissions and whether the app was opened within the following hour", so an emission must be recorded, and no `invitation_emitted` act exists in the vocabulary. Two units diverge on whether system events may be acts at all. Worse, the addendum's A6 states as a **requirement** that the invitation "must be composed from nothing but the configured hour and the Time Bag value — no read of plan state, completion history, or last-open time… if it cannot see whether Sergio has been away, it cannot acquire pressure later, no matter who edits the copy" — an architectural rule about what the notify adapter may read, protecting SM-C3, and it appears nowhere in the spine. AD-17 covers the alarm's timing; nothing covers its inputs. Fix: widen the convention to "one per act — user-initiated or system-emitted, both recorded as fact", add `invitation_emitted`, and add a one-line rule that the notify path receives the hour and the bag value and nothing else.

**H-7 — Album image bytes: deletion is an act, but nothing says who unlinks the file.**
AD-2: "A deletion the user performs (an album entry, the whole album) is itself an act." AD-13: "`AUTHORITATIVE/` holds acts, pool and album image files." FR-18 requires individual deletion and one-action purge. Unresolved: does `album_entry_deleted` also unlink the bytes, or does the file survive as an orphan that the next export writes into the user's chosen — possibly cloud-synced — folder? The round-trip property test passes under both readings, because both produce identical derived read models; the failure it cannot see is a photograph of the inside of the user's home leaving the device after the user deleted it. Fix: one clause on AD-13 — the deletion act is the trigger and the adapter unlinks on commit; `AUTHORITATIVE/` contains exactly the files the derived manifest names.

**H-8 — The settings/validator read surface has no structural owner, and AD-6 makes it worse.**
§7: "Anything a validator needs and a user must never be shown — the FR-26 raw series, FR-30's export state, the Managed path's credit balance — is reachable in settings and nowhere else." The spine honours the pieces (AD-13 routes export state; AD-10 routes key entry) but never names the surface, while AD-6 states that counts are "returned as opaque decisions… never as numbers crossing into the shell". FR-26 requires the raw series to be readable, FR-32 requires a settings-only dictation boolean, and FR-23's dashboard requires real figures. Two units will draw the boundary differently, and the direction of error is asymmetric: exposing a validator read model to a Dispenser widget is the failure §7 exists to prevent. Fix: declare two read facades — the user facade (one card, opaque decisions) and a validator facade (raw series, export state, booleans) that no widget outside `ui/settings` may import, checked the way AD-5 and AD-7 are.

### MEDIUM

**M-9 — AD-4 owns DST but not timezone movement or a moved clock.**
"A DST transition never creates or destroys a period" is the easy half. Acts are stored as UTC instants and the day is `[04:00 local, 04:00 local next)`; if the local zone changes — travel, or a user correcting the device — every historical act re-dates itself, moving SM-1's "≥70% of days", FR-5's three-different-days counter, FR-12's frozen deal window and FR-31's rotation. Two units diverge on whether the zone offset travels with each act or is read from the current device. AD-3 says the core "reads no clock it was not handed"; what the Clock port hands (instant only, or instant plus zone) is undecided. Fix: state which, and state that a period, once closed, never re-dates.

**M-10 — AD-6's opacity rule is over-broad.**
"Signals that are counts… are computed inside the core and returned as opaque decisions… never as numbers crossing into the shell." The examples are internal (declines, comfortable-day run, deal window) and the rule for them is right. The absolute second clause contradicts FR-23 (`4 h 25 min`, `68`, `≈ 3 cajas liberadas`) and §7's validator surface. As written, a careful unit could refuse to expose dashboard totals and a careless one could expose the decline count on the same authority. Fix: split the sentence — invisible mechanism signals cross only as decisions; cumulative achievement figures cross as numbers, and only into the dashboard and settings, never with a denominator (EXPERIENCE.md's denominator rule, which the ERD note covers for stored entities but not for derived read models).

**M-11 — AD-19 does not say what emits `session_ended`.**
A session is `session_started` with no matching `session_ended` in the current domestic day. Nothing says what writes the end: the user stopping, the pocket elapsing, app backgrounding, or nothing at all until the day boundary. The last reading makes an abandoned 10:00 pocket still the live session at 20:00, which changes FR-8's "dealt durations sum to ≤ the declared pocket" arithmetic and where FR-10's checkpoint intervals fall. FR-30 also triggers export "at session end", which presumes an event exists. Fix: one clause naming the emitters.

**M-12 — Epic activation and cluster curation have no act.**
FR-11 and FR-15 turn a dormant Epic active (by user action or accepted suggestion); FR-31 enables and disables Evergreen clusters from onboarding and settings. Neither appears in the vocabulary. One unit folds both into `setting_changed`, another gives each its own act, and the export — the validation evidence — differs in whether "which clusters were on in week 2" is reconstructible. Given AD-1's insistence that settings history be reconstructible, the same argument applies here.

**M-13 — Two deferrals lack revisit conditions, one of them with a structural half.**
Screen-reader behaviour is correctly promoted out of the UX bucket because "traversal order across a one-card surface plus an ambient container is a real decision" — and then left with no revisit trigger and no interim default, so each surface-builder invents semantics. A one-line default ("no custom semantics, no announcements, platform traversal, until specified") would bound it. The iOS deferral has no condition either; low risk, but state one.

### LOW

**L-14 — Bloat, itemised.** The Capability → Architecture Map duplicates the per-AD `Binds:` lines and is derivable from them. The dependency rule appears three times (layer table, AD-5 mermaid, source tree). The Riverpod conventions row declares itself seed inside the invariants table — move it to Stack. The minSdk cell is decision-log rationale inside a version table. AD-10's Rule, AD-17's `USE_EXACT_ALARM` paragraph and AD-13's closing sentence re-argue rulings the PRD already closed. Cutting these would lose nothing an implementer needs and would make the twenty Rules easier to hold in one reading.

**L-15 — FR-32's per-capture dictation boolean is unnamed.** Settings-visible, export-adjacent, and it must not disturb AD-14's origin arithmetic. One word in the pool-fact convention.

**L-16 — AD-3 lacks the mechanical check its siblings have.** AD-5 and AD-7 each get a CI check; banning `Random`, `DateTime.now` and `dart:io` inside `packages/core` is the same kind of check and is cheaper than either.

**L-17 — Enforcement mechanisms are unlocated, and the one enumeration is short.** Seven mechanical guards are asserted across the document (core purity, HTTP chokepoint, string placeholders, catalogue floor, round-trip, forbidden-vocabulary lint, text-scaling lint), while the Testing row says "`tool/` holds **the three** build-time checks" — omitting the two that seal AD-5 and AD-7, the most load-bearing seals in the spine. Say where each lives and what runs it.

**L-18 — Version floors where they matter.** Four packages deferred to cold-start is right for a spine, but `saf_util` is described in the same table as "FR-30's single point of failure", and the `material`/`cupertino` explicit-dependency claim deserves confirmation before someone loses a day to it.

## Strongest thing / biggest risk

**Strongest: AD-1, carried through to AD-19 and AD-20.**
"No plan is ever stored; the day is derived" converts the product's central psychological promise into a property of the data substrate, and then the spine does the hard work of following it to its conclusions rather than stopping at the slogan. It notices that **the session** was smuggled into the derivation's inputs and never declared derived (AD-19), and it notices that **FR-12 hands the Focus Chunk slot to two claimants** and that neither AD-1 nor AD-3 arbitrates (AD-20). It then cashes the invariant out: FR-14's Silent Rescheduler "is therefore not code", and FR-6's Warm Return "needs no path of its own" — two PRD features deleted, not implemented, because the substrate makes them vacuous. That is the highest-value move an architecture document can make, and it is paired with the second-strongest thing here: a consistent habit of converting promises into mechanically checked properties (DB triggers in AD-2, a compile-time-required consent token in AD-8, a generative round-trip property in AD-13, a build-time count in AD-16, dependency and import checks in AD-5 and AD-7). Guarantees stop resting on discipline, which is exactly what §7 asked for when it said the next person to touch the schema will not have read §1.1.

**Biggest risk: the substrate has no theory of its own evolution.**
Everything reduces to a pure function of an append-only log plus a build-time catalogue — and then AD-18 requires shipping new builds onto the validation handsets *during* the four weeks that generate the evidence, while AD-2 forbids ever rewriting what is already recorded. One mid-window build that renames an act, adds a required payload field, or reissues catalogue ids will silently change every derived read model on an upgraded phone: the rotation, the coverage floor, FR-5's counter, SM-1's day count, and the export that is the validation verdict. No AD, no lint, no `tool/` check and not the round-trip property would notice, because the round-trip test generates state under the *current* schema and compares the current derivation with itself. The self-contradiction on settings (C-1) is the same weakness surfacing in the present tense rather than across versions — the one dimension where the spine's own state-mutation identity is not yet settled. Fixing C-1 and adding one compatibility AD would close both, and neither costs more than a paragraph.
