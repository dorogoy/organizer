## Findings

### CRITICAL

**C-1 — The `material` / `cupertino` stack row describes a Flutter release that does not exist.**
The spine commits: "`material` / `cupertino` — **explicit pubspec dependencies** — they left Flutter's core in 3.44 and no longer arrive with `flutter`." Every clause is false as of 2026-08-26:
- The decoupling landed in **3.47** (2026-08-12), not 3.44.
- The packages are **`material_ui` 1.1.0** and **`cupertino_ui`**, both published by flutter.dev. Nothing on pub.dev named `material` or `cupertino` serves this purpose, so the pubspec as described fails `pub get`.
- The core SDK **still includes** the libraries: "While the core SDK still includes these libraries for this release, you can now opt-in to the standalone `material_ui` and `cupertino_ui` packages." `package:flutter/material.dart` is scheduled for *formal deprecation* in the **November 2026** stable — it is neither removed nor deprecated today.

Correct fact and recommended row: opting into `material_ui` / `cupertino_ui` is a legitimate forward-looking choice (the November deprecation is real and this project's cold start is now), but it must be stated as an **opt-in ahead of a November 2026 deprecation**, with the correct package names, not as a forced consequence of a 3.44 removal. Sources: https://flutter.dev/blog/whats-new-in-flutter-3-47 · https://pub.dev/packages/material_ui

**C-2 — The minSdk 33 justification is wrong, and the "sources conflict" is settleable: the on-device recognizer APIs are API 31.**
The spine says minSdk 33 is "set by FR-32's on-device recognizer APIs", that sources conflict between 31 and 33, and that "the official annotation could not be confirmed." Three independent authoritative sources agree on **API 31 (Android 12)**:
1. Google's own **API 31 diff report** for `android.speech.SpeechRecognizer` lists `createOnDeviceSpeechRecognizer(Context)` and `isOnDeviceRecognitionAvailable(Context)` among the **added methods**, alongside four added error constants (`ERROR_LANGUAGE_NOT_SUPPORTED`, `ERROR_LANGUAGE_UNAVAILABLE`, `ERROR_SERVER_DISCONNECTED`, `ERROR_TOO_MANY_REQUESTS`). The `android.speech` package-level diff for API 31 confirms `SpeechRecognizer` as a changed class.
2. Google's **API 33 diff report** for the same class lists only `checkRecognitionSupport(Intent, Executor, RecognitionSupportCallback)`, `triggerModelDownload(Intent)` and `ERROR_CANNOT_CHECK_SUPPORT` — it does **not** list the two methods in question.
3. Platform-generated binding metadata records `ApiSince=31` for `createOnDeviceSpeechRecognizer`.

The "33" in circulation is a conflation with Android 13's *supporting* APIs and its system on-device recognition service.

Consequences for the spine:
- The stated rationale for minSdk 33 collapses, and with it the argument that "were 31 correct and minSdk left there, the defect would be invisible." At minSdk 31 the recognizer pair is present and the affordance would work, not silently fail.
- minSdk 33 remains **defensible on other, real grounds** that the AD should name instead: `POST_NOTIFICATIONS` is API 33 (removes a version branch for AD-17), `USE_EXACT_ALARM` is API 33 (the permission the AD reasons about only exists at 33+), and — most importantly — `checkRecognitionSupport()` and `triggerModelDownload()` are API 33, and those are what FR-32 actually needs to know whether the *Spanish* model is present (see M-2). Rewriting the row on this basis makes minSdk 33 stronger, not weaker.

Sources: https://developer.android.com/sdk/api_diff/31/changes/android.speech.SpeechRecognizer.html · https://developer.android.com/sdk/api_diff/31/changes/pkg_android.speech.html · https://developer.android.com/sdk/api_diff/33/changes/android.speech.SpeechRecognizer.html · https://learn.microsoft.com/en-us/dotnet/api/android.speech.speechrecognizer.createondevicespeechrecognizer

### HIGH

**H-1 — `saf_util` cannot read or write files, so FR-30's export path as specified cannot be built.**
The spine names `saf_util` as "the live SAF path and FR-30's single point of failure", and `plugins/` lists `saf_util` alone. But `saf_util`'s own pub.dev page states: "**this package doesn't provide any read / write functions**" — it offers pickers, directory listing, stat/delete/rename/move/copy, file-descriptor helpers and persisted-permission management. FR-30 writes JSONL for acts and pool plus album image files into a user-chosen tree; AD-13's round-trip property test also reads them back. The read/write package is the same publisher's companion **`saf_stream` 4.0.1** (bytes and stream APIs, overwrite/append, copy-to/paste-from local, minSdk 21). Either add `saf_stream` to the stack, `plugins/` and the "flaky dependencies" Deferred entry, or state explicitly that writes go through `saf_util`'s file descriptors. Sources: https://pub.dev/packages/saf_util · https://pub.dev/packages/saf_stream

**H-2 — The `flutter_secure_storage` row misstates both the crypto library and where the AES key lives.**
Two errors in one row describing the BYOK key's protection:
- **Not Tink.** The v10 changelog states Google recommends Tink "but Tink does not support biometrics, so custom ciphers have been reintroduced." The plugin migrated off Jetpack Crypto to its **own** cipher implementations, not to Google Tink.
- **The AES key is not in the KeyStore under the default config.** With the default `RSA_ECB_OAEPwithSHA_256andMGF1Padding` key cipher, the **RSA keypair** is KeyStore-resident and *wraps* the AES key, which is stored encrypted in SharedPreferences. Only selecting the `AES_GCM_NoPadding` **key cipher** puts an AES key directly in the KeyStore ("KeyStore AES stores the key directly in Android KeyStore"), and that is the biometric path (API 28+ for enforced biometrics).

Version 11.0.0 and minSdk 23 are correct. Fix the description, and decide explicitly which key cipher the BYOK key uses — that choice, not the plugin name, is the threat model. Sources: https://pub.dev/packages/flutter_secure_storage/changelog · https://github.com/juliansteenbakker/flutter_secure_storage

**H-3 — Gemma 4 E4B's disk footprint is understated by ~1.2 GB, in the direction that matters.**
The spine says "~2.5 GB on disk, 4–5 GB RAM", and the Deferred entry rests on "the user's standing constraint that not every handset can host a model, nor every user spare the storage." The official litert-community model card gives total **3.66 GB** ("a text decoder with 2.24 GB of weights and 0.67 GB of embedding parameters"); the Android benchmark table reports model size **3654 MB** with peak memory **3283 MB** on CPU and **710 MB** on GPU. The ~2.9 GB number in circulation is the *web*-optimised variant. Note also that the card publishes **peak memory**, not a minimum-RAM figure, so "4–5 GB RAM" is an unsourced inference (third-party guides put CPU-only E4B nearer 10 GB of free system RAM — sources conflict, and the card is the one to trust). Correct the disk figure upward; it is the number a storage-constrained user feels. Sources: https://huggingface.co/litert-community/gemma-4-E4B-it-litert-lm · https://ai.google.dev/gemma/docs/core

**H-4 — "No mature Flutter package exists" for the Local path is contradicted by a live, popular package.**
`flutter_gemma` 1.6.5 (verified publisher sashadenisov.dev, 424 likes, published within the last week) ships both a **MediaPipe engine** for `.task`/`.bin` models and a **LiteRT-LM FFI engine** for `.litertlm`, and explicitly lists Gemma 4 E2B/E4B on Android arm64-v8a with CPU and GPU backends — exactly the deployment path the Deferred entry says has no package. "Mature" is a judgment call and a hand-written channel may still be the right choice, but the entry's *cost estimate* (a Kotlin platform channel over MediaPipe/LiteRT-LM) is likely overstated, and the entry should either cite the package and say why it is rejected, or drop the claim. Source: https://pub.dev/packages/flutter_gemma

### MEDIUM

**M-1 — Target SDK 36 is one platform generation behind, and two targetSdk-36 behaviours that bear on the UX invariants are unstated.**
Android 17 = **API 37** shipped stable **2026-06-16**. Play requires target 36 from 2026-08-31 and 37 from Aug 2027, and AD-18 forgoes store distribution entirely — so pinning 36 is fine, but the table's "Verified current 2026-08-26" implies 36 *is* current, and it isn't; the row should say "36, deliberately one behind 37." More materially, targeting 36 carries consequences the spine never records and that touch its own cross-cutting rules: apps targeting Android 16 **cannot opt out of edge-to-edge**, and large-screen **resizability cannot be opted out**. Both interact with the never-`maxLines` / 200%-text-scaling / one-card-surface conventions. Sources: https://support.google.com/googleplay/android-developer/answer/11926878 · https://developer.android.com/google/play/requirements/target-sdk

**M-2 — AD-11's dictate gate is insufficient for Spanish, and this is the real argument for minSdk 33.**
`isOnDeviceRecognitionAvailable()` answers whether an on-device recognition *service* exists; it does not answer whether the **Spanish** model is downloaded. On-device language packs are per-language downloads managed by the Google app (`com.google.android.googlequicksearchbox`), and API 31 added `ERROR_LANGUAGE_UNAVAILABLE` / `ERROR_LANGUAGE_NOT_SUPPORTED` precisely for this case. Since Spanish is the only shipped locale, the current gate can pass and then fail at recognition time — which is not FR-32's "the affordance is simply not present", it is a broken affordance. The APIs that answer the question are API 33's `checkRecognitionSupport(Intent, Executor, RecognitionSupportCallback)` and `triggerModelDownload(Intent)`. AD-11 should gate on `checkRecognitionSupport` for the `es` locale, and decide whether a missing model hides the affordance or triggers a download. Sources: https://developer.android.com/sdk/api_diff/33/changes/android.speech.SpeechRecognizer.html · https://developer.android.com/reference/android/speech/SpeechRecognizer

**M-3 — `RECEIVE_BOOT_COMPLETED` is required by AD-17 and named nowhere.**
AD-17 commits to an inexact alarm "rescheduled after boot". That requires `android.permission.RECEIVE_BOOT_COMPLETED` in the manifest plus a `BOOT_COMPLETED` receiver. The permission is normal/install-time, so "runtime permissions are exactly three" survives — but the AD reads as an exhaustive permission list and is not one. Add the distinction between runtime and manifest permissions explicitly, since the AD's whole point is that the permission surface is closed. Source: https://developer.android.com/develop/background-work/services/alarms/schedule

**M-4 — AD-2's triggers force a `.drift` schema file, and the migration path for them is unstated.**
drift's documentation states plainly: "In drift, triggers can only be declared in **.drift files**." AD-2's "the `acts` table carries SQL triggers that raise on `UPDATE` and on `DELETE`" therefore constrains schema authoring (`store/` must hold a `.drift` file, not only Dart table classes), and — because AD-18 makes install-on-top with a schema migration the release ritual — the triggers must be reasserted by the migration steps. This is the one place AD-2's database-level enforcement can silently disappear: a migration that recreates `acts` without recreating the triggers leaves the invariant as discipline again. Worth one sentence in AD-2 and a test in `tool/`. Sources: https://drift.simonbinder.eu/sql_api/drift_files/ · https://pub.dev/documentation/drift/latest/drift/Trigger-class.html

**M-5 — Four stack rows carry no version where the version is what makes the invariant hold.**
Riverpod, `camera`, `google_mlkit_face_detection` and `saf_util` are all "pin at cold-start". For two of them the version is load-bearing: `saf_util` is named FR-30's single point of failure (and, per H-1, the wrong package for writing); `google_mlkit_face_detection`'s version determines its declared minSdk/compileSdk and its 16 KB page-size alignment. Current values found: `flutter_riverpod` 3.4.2, `camera` 0.12.0+2 (flutter.dev, Android 24+), `google_mlkit_face_detection` 0.15.1 (minSdk 21, target/compile 35), `saf_util` 3.1.0. Also unpinned: the `uuid` package behind the UUIDv7 convention (4.6.0 supports RFC 9562 v7).

### LOW

Record the template's live defaults rather than deferring to them. Sources: https://blog.jetbrains.com/kotlin/2026/06/kotlin-2-4-0-released/ · https://flutter.dev/blog/whats-new-in-flutter-3-47

Sources: https://meetily.ai/llm-privacy/gemini · https://www.protecto.ai/blog/openai-data-privacy/ · https://anarlog.so/blog/anthropic-data-retention-policy/

**L-3 — `setShowBadge(false)` is a default, not a guarantee.** Correct API (channel APIs are API 26) and correct choice. Two facts worth recording: a channel's importance **cannot be changed after creation** — which actually strengthens AD-11's "created once and never a second channel" — and the user can override both importance and badge display at any time. AD-11 currently reads as if the code owns the outcome. Source: https://developer.android.com/develop/ui/views/notifications/channels

**L-4 — AD-11's carve-out is strong for dictate and weak for notify.** `flutter_local_notifications` 22.3.0 is alive and maintained, supports inexact scheduling modes, and can configure channel importance and badges; its own docs reproduce exactly the `USE_EXACT_ALARM` vs `SCHEDULE_EXACT_ALARM` reasoning AD-17 gives. So for notify, the platform channel is a preference, not a case where "the guarantee *is* an OS API" and a plugin could degrade it. For dictate the argument does hold (the on-device-forcing creator has no equivalent plugin path). Say so asymmetrically, or the rule reads as post-hoc. Source: https://pub.dev/packages/flutter_local_notifications

**L-5 — 16 KB page-size alignment is fine but only because of the 64-bit commitment.** ML Kit's `arm64-v8a` and `x86_64` face-detection `.so` files are 16 KB aligned; `armeabi-v7a` and `x86` are still 4 KB. Play has rejected non-compliant native code since 2025-11-01 (moot here — no store distribution), but misaligned libraries can fail to load on 16 KB-page devices. Safe given "ML Kit is 64-bit only", provided the build's `abiFilters` actually exclude 32-bit ABIs — which is currently implied, not stated. Sources: https://github.com/googlesamples/mlkit/issues/986 · https://android-developers.googleblog.com/2025/05/prepare-play-apps-for-devices-with-16kb-page-size.html

**L-6 — AD-8's "on-device face refusal" is a filter, not a property.** ML Kit face detection is best-effort: it will miss faces at extreme angles, small scale, heavy occlusion, or faces present only as reflections or in printed photos within the frame. The spine treats absence of a detection as a fact about the image. Given AD-8 makes the refusal a compile-time capability gate, the *strength* of the gate should be described honestly — the token is withheld when a face is **detected**, which is not the same as guaranteeing no face left the device.

**L-7 — UUIDv7 monotonicity is unpinned.** `uuid` 4.6.0 supports RFC 9562 v7. AD-3 breaks ties by "least-recently-dealt, then by stable id", so v7 ordering within a single millisecond is (weakly) load-bearing for determinism. Pin the package and note whether monotonic generation is required.

## Notes on method and residual uncertainty

- **API 31 vs 33 was settled from Google's own API-diff reports** (both the API 31 and the API 33 pages for `android.speech.SpeechRecognizer`, plus the API 31 `android.speech` package diff), cross-checked against platform-generated binding metadata (`ApiSince=31`). The live `developer.android.com/reference/android/speech/SpeechRecognizer` page could not be rendered into readable per-member "Added in API level" annotations by the fetch tool; the diff reports are the same publisher and are unambiguous, and no source found placed the two methods at 33. Treat the question as closed at **API 31**.
- **Sources conflict on Gemma 4 E4B RAM.** The official model card publishes peak-memory benchmarks (3283 MB CPU / 710 MB GPU on an S26 Ultra), not a minimum-RAM requirement; third-party hardware guides give ~6 GB VRAM or ~10 GB system RAM for CPU-only inference. The spine's "4–5 GB" matches neither. Stated here as a conflict rather than resolved.
- **Not independently verifiable:** "Android 13 predates the validation handsets by years" (a claim about three specific private handsets) — benign, but it is the only remaining support for minSdk 33 once C-2 is applied, so the AD should carry a real technical reason as well.
- **Not checked (out of lens):** the internal consistency of AD-1…AD-20 against the PRD/UX inputs, FR numbering, and the derivation logic. This review covers only externally verifiable technology claims.
