## Findings

### F-1 — LOW — "Play requires 37 from Aug 2027" is a projection, not yet a posted requirement

- **Claim (spine, Stack table):** "Play requires 36 from 2026-08-31 and 37 from Aug 2027, so 36 is current-enough and 37's edge-to-edge and resizability changes are a known follow-up"
- **What the web actually says:** Google Play's live policy page ("Target API level requirements for Google Play apps", support.google.com, fetched 2026-08-27) states: "Starting August 31, 2026: New apps and app updates must target Android 16 (API level 36) or higher…" with an extension option to November 1, 2026. The newest row in the official requirements table is **Android 16 / Aug 31, 2026**. No API-37 row or 2027 deadline is posted anywhere on the page as of today. The "37 from Aug 2027" date is an extrapolation from Play's standing "target within one year of the latest release" pattern — plausible and consistent with the historical cadence, but not a posted requirement.
- **Impact:** Minimal. The 36-from-2026-08-31 half is confirmed verbatim, which is the half the decision rests on ("36 is current-enough"). The spine's own AD-18 says "No store distribution," so Play deadlines are context rather than a compliance constraint for this build. The conclusion is unaffected; only the phrasing states a projection as fact.
- **Source:** https://support.google.com/googleplay/android-developer/answer/11926878 (live fetch 2026-08-27); https://developer.android.com/google/play/requirements/target-sdk (search snippet confirms the same Aug 31 2026 / API 36 text).

### F-2 — INFO — ML Kit "64-bit only" is loose wording for Android; the prescribed action is nonetheless correct

- **Claim (spine, Stack table):** "`google_mlkit_face_detection` 0.15.1 … 64-bit only; `abiFilters` must exclude 32-bit ABIs, which also keeps the 16 KB page-size alignment"
- **What the web actually says:** On iOS the plugin README states ML Kit does not support 32-bit architectures (i386/armv7). On **Android**, ML Kit face detection *does* ship 32-bit native libraries — and that is precisely the problem: Google issue tracker 458518879 and googlesamples/mlkit issues #986/#1024 report "32-bit face-detection native libraries are still built with 4 KB page alignment (not 16 KB)" while the 64-bit libraries are 16 KB-aligned. So the accurate mechanism is "ML Kit's 32-bit Android libs are 4 KB-aligned and break 16 KB compliance; excluding 32-bit ABIs removes them," not "64-bit only." The operative instruction (exclude 32-bit ABIs via `abiFilters`) is verified as exactly the community-documented and issue-tracker-consistent workaround, and the 16 KB consequence claimed by the spine is real.
- **Impact:** None on the decision; the build instruction is right. Worth a wording fix if the spine is ever revised, so a future story doesn't conclude ML Kit cannot run on 32-bit Android at all (it can — it just shouldn't ship there in this app).
- **Sources:** https://issuetracker.google.com/issues/458518879 ; https://github.com/googlesamples/mlkit/issues/986 ; https://github.com/googlesamples/mlkit/issues/1024 ; https://developer.android.com/guide/practices/page-sizes ; plugin README (pub.dev/packages/google_mlkit_face_detection, iOS section).

### F-3 — INFO — flutter_secure_storage "v10 rejected Tink for lacking biometric support": outcome verified, causal sentence is a paraphrase

- **Claim (spine, Stack table):** "It did **not** move to Tink (v10 rejected Tink for lacking biometric support). Under the default RSA-OAEP cipher the AES key is RSA-wrapped **in SharedPreferences**, which FR-28 forbids in words — so the AES-in-KeyStore cipher is configured explicitly, or the requirement is broken by default."
- **What the web actually says:** The live pub.dev README (v11.0.0) confirms every load-bearing element: "Version 10.0.0 introduces a major security update with custom cipher implementations. The deprecated Jetpack Security library's `encryptedSharedPreferences` is no longer recommended"; "New default ciphers: RSA OAEP (key cipher) + AES-GCM (storage cipher)"; the cipher table shows `AndroidOptions()` default = "RSA-wrapped AES" with no biometric support, while `AES_GCM_NoPadding` as key cipher "stores the key directly in Android KeyStore"; the migration section confirms encrypted data (and its wrapped key) live in SharedPreferences. So: not Tink ✓; RSA-wrapped AES key by default ✓; explicit config required for AES-in-KeyStore ✓. The specific sentence "v10 rejected Tink **for lacking biometric support**" (the motivation) is consistent with v10 simultaneously introducing biometric-capable ciphers, but no live page states that exact motivation — it is the maintainer's history compressed, not contradicted.
- **Impact:** None. The decision (configure the AES-in-KeyStore cipher explicitly, or use the fork) is supported by verified facts.
- **Source:** https://pub.dev/packages/flutter_secure_storage (README, live fetch 2026-08-27).

### F-4 — INFO — Gemma figures cited against the correct card; note the ecosystem's own size table differs

- **Claim (spine, Stack table):** "Gemma 4 E4B … **3.66 GB** on disk | 3654 MB Android model size, ~3283 MB peak memory, per the official model card — not the ~2.5 GB the first draft claimed"
- **What the web actually says:** The official LiteRT-LM model card (huggingface.co/litert-community/gemma-4-E4B-it-litert-lm) states "The model file size is 3.66 GB" and its Android benchmark table lists Model size (MB) = **3654** and CPU memory = **3283** (S26 Ultra, CPU backend). All three spine numbers are exact matches to the cited card. Informational note: `flutter_gemma`'s own README capability table lists Gemma 4 E4B at "4.3GB" (a different variant/format), and the same model card notes Gemma 4 is also reachable on supported devices via Android AI Core as Gemini Nano — neither contradicts the spine's storage-constraint figure for the LiteRT-LM on-disk path it cites.
- **Impact:** None.
- **Source:** https://huggingface.co/litert-community/gemma-4-E4B-it-litert-lm (live fetch 2026-08-27); https://pub.dev/packages/flutter_gemma .
